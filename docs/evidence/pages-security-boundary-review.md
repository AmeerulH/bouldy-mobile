# Auth, gyms and route forms: scoped security review

Single-agent application of the security-review skill to the five newly ported commands, their snapshot reads, auth integration and forms. No high-confidence vulnerabilities identified in that scoped review. This is not release approval or a FastAPI/backend audit.

- Signup uses the original registration-then-login sequence. Browser credentials remain HTTP-only; native Signup uses the same SecureStore/identity epoch path as Login. No password persistence, URL credentials or new auth endpoint was introduced. Synthetic registration tests cover optional/trimmed fields and failure after successful registration without an automatic retry.
- The adapter now allows exactly 11 named commands. Browser JSON writes retain exact Origin checks and the streaming one-MiB body limit. Only repeated `style` strings may be arrays; all other fields stay strings/numbers. Fields are copied explicitly into the source command payloads; arbitrary URL/method forwarding remains unavailable.
- All non-auth mutations validate identity. Existing session-bound commands retain owner checks. Add gym and Start session do not require an existing session. Start session obtains user ID and the UTC date server-side, ignoring forged owner/date/duration fields.
- Session-context route creation also checks session ownership, matching gym and active visit before creating the shared gym route. This carries page/controller restrictions into the trusted boundary; direct invalid requests are rejected rather than relying on hidden controls. This is stronger than the old addRoute action alone, which trusted its page context. Normal source messages/navigation and valid payloads are preserved.
- Edit retains the source action's same-gym check. Form reads reject retired or wrong-gym routes. Route metadata/record IDs and attempt history remain unchanged by edits. The source backend owns authorization for shared gym/route mutations; this work does not add an admin-only model or claim new backend guarantees.
- New gym/form reads validate identity and avoid unnecessary journal reads. Foreign session-form reads fail before returning data. Form state is keyed to the account/resource; existing auth generation checks reject late responses from a prior identity.
- React text rendering is used for names, locations and routes. Destinations are constructed from validated IDs/source constants, never user-supplied URLs. No private cache, write queue, replay, retry or production mutation was added.

Evidence: 54 passing unit/adapter tests in `pages-tests.log`; native fixture observations in `pages-native-review.json`; local production HTTP checks in `pages-production-smoke.json`. Twenty exported client/native bundles contained none of the selected upstream/fixture ASCII markers (`pages-bundle-boundary.json`); this limited scan is not a full binary audit.

Still open: two-account end-to-end isolation, backend permission/concurrency/uniqueness behavior, production host/cookie/adapter configuration, physical devices and standalone binaries. The live 4010 fixture process is the earlier mock; fresh 4012 test processes exercise the enhanced registration/failure assertions. Native synthetic Signup does not prove persistence of a genuinely new account. No production records were created.
